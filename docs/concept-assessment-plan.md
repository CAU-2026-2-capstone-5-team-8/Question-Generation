# 개념별 진단 문항 개편 — 2026-10-03

## 목표와 범위

책 목차는 공통 개념과 연결한다. 사용자 평가는 각 개념에서 뜻·성질을 구별하고, 계산·적용하고, 설명·관계를 판단할 수 있는지 기록한다. 이전 용어·배경지식·독해 총점을 새 문항의 목표로 쓰지 않는다. 선택형 추론 문항은 설명을 구별하는 능력을 관찰하며 자유 서술 능력을 증명하지 않는다.

첫 범위는 선형대수의 matrix, vector, linear system, linear independence, basis, orthogonality 6개 개념 × 3가지 수행 목표 = 18문항이다. 분야의 모든 개념이 평가됐다고 표시하지 않는다. 문제 목표와 오개념을 설정 파일로 관리하고, 목차 연결 근거와 입력 해시를 보존한다. 목차는 평가 대상 선정 근거이며 정답이나 본문 난이도의 근거가 아니다.

## 구현 순서

1. ML: 기존 스키마와 별도로 `concept-question-spec-v2`와 목차 기반 설계서 생성 경로를 추가한다.
2. Question-Generation: `generated-question-v5`의 생성·검증·재시도·검토 자료 출력 경로를 추가한다. 같은 개념에서도 목표별 질문을 실제로 달리 생성한다.
3. Backend: 새 계약을 엄격히 검증하고 승인 문항만 등록한다. 기존 발급 문항과 답변 스냅샷을 보존한다. 새 문항은 개념·수행 목표를 균형 있게 고른다.
4. ML/Backend/Frontend: 지문 제공 여부를 전달하고 지문 기반 수행을 사전 지식과 분리한다. 자기평가는 별도로 남긴다.
5. 실제 18문항을 생성하고 검토 가능한 질문·보기·정답·해설·목표 자료를 만든다. 자동 검증과 사람 검토를 구분한다.
6. 계약 오류, 정답 노출, 중복 보기, 문항 목표 변경, 지문 결과 혼합, 기존 버전 회귀를 검사한다.

## 생성과 검토 기준

- 의미 문항: 단어 번역보다 정의·성질·조건을 구별한다.
- 적용 문항: 구체적인 값이나 상황을 바꾸어 계산·판단한다.
- 추론 문항: 근거, 반례, 조건의 필요성을 판단한다. 용어만 알아도 맞히는 문제로 대체하지 않는다.
- 오답은 설정된 오개념에 대응해야 한다. 길이, 맞춤법, 부자연스러운 표현으로 정답이 드러나면 수정한다.
- 초기 18문항은 `prior-knowledge`다. 규칙을 제공하는 `provided-information` 문제는 다른 관찰로 저장하고 사전 지식 지도·추천에 합치지 않는다.
- 기존 생성기의 영어 원문 정책을 유지한다. 한국어 표시 번역은 별도 표현 버전으로 다루며 원문의 정답 인덱스와 개념 ID를 바꾸지 않는다.
- 자동 구조 검사는 수학적 정확도나 진단 타당성의 사람 검토를 대신하지 않는다. AI가 검토자를 사칭하는 승인 기록을 만들지 않는다.

## 완료 확인

설계서와 실제 생성 자료를 확인하고 테스트 결과를 기록한다. 새 문제은행 활성화는 검토 결과가 준비된 뒤 진행한다. 생성 결과 자체와 과거 사용자 응답을 덮어쓰지 않는다. 운영체제 확대·적응형 검사·숙련도 확률 보정은 이번 범위에 포함하지 않는다.


## 이번 구현 결과

- 설계서 18개를 실제 canonical 목차 근거로 생성했다. 의미·적용·추론 목표와 오개념이 서로 다르다.
- 새 Gemini 생성 명령과 API 없는 로컬 초안 경로를 추가했다. 이번 실제 출력은 `codex-local-draft` 18개다.
- `generated-question-v5`의 엄격한 등록 계약, 추가 DB 마이그레이션, 발급 snapshot과 응답 전달을 구현했다.
- 새로운 bank의 9문항 선택은 수행 목표·개념의 다양성과 동일 사용자·분야의 이전 응답 노출을 고려한다.
- `concept-abilities-v2`는 사전 지식·지문 제공 후 수행·조건 불명 응답을 분리한다. 새 지도와 추천은 사전 지식만 사용한다.
- 로컬 RN `/question-review`에서 18개 후보의 질문·보기·정답·해설·목표를 확인할 수 있다. 답변은 진단에 저장하지 않는다.

검증: Backend 전체 161개(실제 ML 계약 포함, skip 0), 별도 v5 snapshot/import 4개, ML 전체 322개,
Question-Generation 112개 통과. 생성기의 live 테스트 2개는 기본 정책대로 제외했다. RN 타입 검사·린트·웹 빌드 통과.
실제 브라우저의 1280px/390px 검토 화면에서 18문항 이동·선택·정답 표시·경계 버튼·진단 화면 진입을 확인했다.
가로 넘침과 실행 오류가 없었다. 실제 재실행 ML API에서 동일 개념의 사전 지식 오답·지문 후 정답·조건 불명 정답이
서로 다른 집계에 들어가는 것도 확인했다. 새 화면의 네이티브 실기기 검증은 수행하지 않았다.

남은 단계: 후보 문항의 사람 검토와 승인 결과에 따른 실제 진단 bank 교체다.
Gemini로 추가 생성하기로 선택할 경우에는 별도로 외부 전송 승인이 필요하다.
외부 전송에 대한 자동 승인 거절을 우회하지 않았다. 기존 실제 bank와 사용자 응답은 새 후보로 덮어쓰지 않았다.

## 수식 표시 후속

문제 JSON 구조를 유지하고 텍스트 필드에 Markdown·LaTeX를 적용했다. 생성 프롬프트는 v2로 버전이 바뀌며,
ML/Backend 계약은 v1과 v2를 모두 읽는다. 로컬 초안 18개는 표기만 정리하여 새 ID와 별도 출력 폴더
`data/generated/concept-assessment-math-v2`에 보관했다. 정답 인덱스와 개념·측정 목표는 유지했다.
로컬 Backend의 검토 화면도 이 폴더를 사용한다. 사람 승인과 실제 bank 활성화는 여전히 별도 단계다.

검증: 생성기 127개 통과(live 2개 제외), 표시 컴포넌트 5개, Backend v5 계약 5개, ML 설계 계약 2개 통과.
18개 실제 산출물의 ML 계약과 텍스트 108개 필드의 KaTeX 표시 검사도 통과했다.
RN 타입 검사·린트, 웹·iOS·Android 번들 생성 통과. 브라우저에서 18문항을 모두 확인하고
320/390/768/1280px의 가로 넘침, 수식 클릭과 스페이스 키 선택, 실행 오류와 외부 요청을 확인했다.
표시 오류·페이지 넘침·실행 오류·수식 관련 외부 요청은 없었다. 네이티브 실기기 검증은 수행하지 않았다.
형식과 검토 절차는 [문제 본문 형식](question-content-format.md)을 참고한다.

## 사람 검토 준비 후속

`concept prepare-review`로 판정을 비워 둔 검토표와 문항 자료를 별도 폴더에 생성하고,
`concept review-status`로 각 개념·수행 목표의 판정 현황을 확인할 수 있다.
설계서와 후보 메타데이터를 함께 검증하고, 문항 수정 후 이전 생성 ID의 검토 결과가 섞이거나
검토 기록이 중복·누락되면 오류로 처리한다. 작성 중인 검토 폴더는 덮어쓰지 않는다.

현재 범위는 6개 개념 × 3개 수행 목표에 후보가 각각 1개다. 후보가 빠진 셀은 없지만
대체 문항은 없으며, 이번에 준비한 판정표의 18개 행은 모두 미검토 상태다.
사람이 수정 필요로 판정한 문항부터 새 버전으로 보강하고 재검토한 뒤 승인된 생성 ID만 등록한다.
운영체제 확대나 대체 문항 대량 생성에 앞서 첫 18개를 실제로 검토하는 순서를 유지한다.

## 2026-10-04 검토 방식 변경과 후속

사용자가 AI에 문항의 내용 판단과 수정을 위임했다. 따라서 위의 사람 검토 대기를 현재 작업의
필수 조건으로 삼지 않는다. 대신 실제 검토 주체를 구분해 보존한다. Codex의 AI 내용 검토와
10문항 수정 결과는 [별도 기록](concept-ai-review-2026-10-04.md)에 정리했다.
`ai-question-review-v1` 판정을 Backend v5 등록 경로의 `aiReview`로 전달하며,
자동 구조 검사 통과를 승인으로 바꾸거나 AI 판정을 `humanReview`에 넣지 않는다.
후속 과제는 실제 응답으로 난도·변별력 확인, 문항별 대체 후보 확보다.
